# Phase 0 — Research: Voice-First Conversation MVP

This file resolves every NEEDS-CLARIFICATION-level uncertainty for the locked tech stack. Each entry follows the **Decision / Rationale / Alternatives considered** form. No item below is left open; if a future signal forces a change, it triggers a plan revision.

---

## 1. AI client transport — fetch + SSE, no SDK

- **Decision**: Implement `src/lib/ai.ts` with a single `sendChatStream(messages, opts)` function that calls `POST {VITE_AI_BASE_URL}/chat/completions` via `fetch`, sets `stream: true`, parses Server-Sent Events from the `ReadableStream` body, and yields `{ delta: string }` chunks until the SSE stream emits `[DONE]`.
- **Rationale**: The proxy is OpenAI-compatible and the SSE format is stable. Pulling in `openai` (~150 kB minified) buys nothing we use. A bespoke 50-line fetch loop has zero transitive deps and is trivially testable. §VII (YAGNI).
- **Alternatives considered**: (a) Official `openai` SDK — rejected for size and dep churn; (b) `eventsource-parser` package — borderline; rejected since the SSE format we consume is the trivial subset (one `data:` per event, terminated by `[DONE]`); (c) Long-poll non-streaming — rejected because §IV's 1500 ms LLM budget is unattainable without streaming.

## 2. Sentence chunking heuristic for streaming → TTS

- **Decision**: In `ai.ts`, accumulate streamed deltas into a buffer and emit a "sentence ready" signal whenever the buffer ends with `.`, `!`, `?`, or `…` followed by whitespace **or** the buffer exceeds 200 characters without a terminator. Comma-delimited clauses are NOT cut. The orchestrator forwards each sentence to `tts.ts`, which queues utterances back-to-back to avoid the gap between `SpeechSynthesisUtterance.onend` and the next `speak()`.
- **Rationale**: The §IV TTS budget is "first audio chunk ≤ 700 ms after first sentence is buffered." Sentence-level chunking is the smallest unit the browser TTS treats as a complete utterance with prosody; finer chunks (clauses, words) sound robotic and are blocked by the synthesizer's queueing. The 200-char hard cap protects against pathological one-sentence paragraphs.
- **Alternatives considered**: (a) Speak the full reply once streaming completes — rejected, blows §IV; (b) Chunk by clause (commas) — rejected, prosody breaks; (c) Chunk by every N tokens — rejected, ignores natural prosody and worsens the perceived experience.

## 3. STT — Web Speech API with iOS Safari auto-restart

- **Decision**: Wrap `(window as any).webkitSpeechRecognition || (window as any).SpeechRecognition` in `src/lib/stt.ts` with `lang='en-US'`, `interimResults=true` (ingested only for VAD heuristic; never surfaced — FR-026/SC-011), `continuous=false`. On `onend` while we still expect to be recognizing, automatically call `start()` again up to 3 consecutive times within a single learner turn; after 3 in a row, surface an error and let the orchestrator end the turn.
- **Rationale**: iOS Safari's webkitSpeechRecognition spontaneously fires `onend` after ~30 s or on transient mic glitches even when the user is still speaking; the published mitigation is automatic restart with a small retry count. The 3-attempt cap stops infinite loops when permission is silently revoked.
- **Alternatives considered**: (a) Use `MediaRecorder` + Whisper-via-proxy — deferred under §VI as a measured-failure fallback (see §10 below); (b) Use `vosk-browser` — rejected, ~10 MB model breaks bundle constraints; (c) Trust webkitSpeechRecognition without restart — rejected, fails on iOS in practice.

## 4. TTS — SpeechSynthesis with en-US voice preference

- **Decision**: `src/lib/tts.ts` waits for `SpeechSynthesis.onvoiceschanged` to populate the voice list, then prefers (in order): a voice with `lang === 'en-US'` and `name` matching `/Samantha|Allison|Ava|Joanna|Natural/i`, then any `lang === 'en-US'`, then the platform default. Voice selection is computed once at module init and cached. Each utterance uses `rate=1.0`, `pitch=1.0`, `volume=1.0`.
- **Rationale**: macOS and iOS ship "Samantha"/"Allison" voices that sound substantially less robotic than the platform default; on Windows, "Microsoft Aria" matches `/Natural/`. Caching avoids a per-utterance scan. Default values for rate/pitch keep the warm/casual feel; non-default values cross into uncanny territory.
- **Alternatives considered**: (a) Always use platform default — rejected, the default on Linux is famously bad; (b) ElevenLabs / Google Cloud TTS — rejected under §VI until measured failure of the free tier.

## 5. VAD — energy-based AnalyserNode (amended 2026-04-28)

- **Decision (amended 2026-04-28)**: Hand-roll a simple energy-threshold VAD over `AudioContext.AnalyserNode`. Spec: `fftSize=512`, `smoothingTimeConstant=0.5`, frame loop via `requestAnimationFrame`; average frequency-bin amplitude > **25** counts as speech, ≥ **35 frames** of below-threshold (~600 ms at 60 fps) after speech-detected counts as endpoint. `startVAD(callbacks)` returns a handle whose `stop()` releases the mic stream and closes the AudioContext. Approximately 30 lines, zero external dependencies.
- **Rationale (amended 2026-04-28)**: The original choice (`@ricky0123/vad-web`) failed under Vite 8's rolldown bundler with `Calling 'require' for "onnxruntime-web/wasm" in an environment that doesn't expose the require function`. The vad-web library uses a CJS `require()` call to obtain ORT internals, and rolldown refuses to translate runtime `require()` to dynamic ESM. The published workarounds (UMD bundle imports, custom Vite resolve aliases, polyfilling `require` globally) are all hacks that fight the bundler. An energy-threshold VAD eliminates the dep entirely, drops the precache footprint by ~417 kB (vad-web onnx + ORT wasm), and removes 4 transitive npm advisories. Trade: lower robustness in noisy environments. For the MVP target context (solo learner, quiet room, daily practice), energy-threshold is sufficient; if SC-001 measurements expose excessive false endpoints in user testing, the swap path is documented in this same module file (`src/lib/vad.ts`) so a future feature can plug in a different detector behind the same `startVAD(callbacks): VADHandle` surface.
- **Alternatives considered (amended 2026-04-28)**: (a) Original `@ricky0123/vad-web` — rejected after measured-failure on Vite 8 rolldown; the library's own published workarounds for Vite are hacks (UMD bundle, require polyfill, alias rewriting); (b) Pure-JS VADs without onnx (vosk-js, etc.) — rejected, materially worse accuracy or much larger model download; (c) Server-side VAD — rejected, adds an external network dep beyond the locked AI proxy and breaks §VI; (d) Stick with vad-web by patching the package via `pnpm patch` or a postinstall codemod — rejected, fragile across upgrades and adds a moving piece to the dep tree; (e) Use the Web Speech API's own end-of-speech heuristic — rejected, iOS Safari's `webkitSpeechRecognition.onend` is the unreliable signal that motivated wanting a separate VAD in the first place (see §3).

## 6. PWA — vite-plugin-pwa with auto-update + model precache

- **Decision**: `vite-plugin-pwa` with `registerType: 'autoUpdate'`. `manifest`: `name: 'Boom — Daily English Tutor'`, `short_name: 'Boom'`, `display: 'standalone'`, `start_url: '/'`, theme/background colors set to the bubble palette (chosen during implementation, not in plan). `workbox.globPatterns` precaches the app shell (`**/*.{js,css,html,svg,png,woff2}`). `workbox.runtimeCaching` adds a `NetworkOnly` rule scoped to the AI proxy origin (so AI traffic is never cached) and a `CacheFirst` rule scoped to the vad-web onnx model URL (one-time download, then cached).
- **Rationale**: Auto-update keeps the PWA fresh without prompting the user — fits the "no clutter" voice-first principle. Excluding AI requests from caching is a §V privacy invariant. Precaching the vad-web model removes the 1 MB cost from the second load onward.
- **Alternatives considered**: (a) `prompt` registerType (ask user before update) — rejected, breaks the flow; (b) Workbox CDN — rejected, adds an external network dep beyond the AI proxy (against reviewer-acceptance #5).
- **Known peer-dependency footnote (interim)**: As of feature 001, `vite-plugin-pwa@1.2.0` declares its peer range as `vite ^3 || ^4 || ^5 || ^6 || ^7`, while this project pins `vite@^8.0.10`. The plugin works at runtime against vite 8 (build emits `dist/manifest.webmanifest` and `dist/sw.js` cleanly); only the published peer range lags. We carry `.npmrc` with `legacy-peer-deps=true` plus an inline rationale comment so `npm install` succeeds reproducibly. Remove the `.npmrc` entry once an upstream `vite-plugin-pwa` release widens its peer range to include vite 8. This is not a constitutional or plan deviation — it is a temporary install-time workaround for a peer-range mismatch, documented for transparency and future cleanup.

## 7. State management — Zustand (single store)

- **Decision** *(amended 2026-04-28)*: One Zustand store in `src/state/conversation.ts` exposing `useConversationStore` plus a small set of selector hooks (`useTurns()`, `useBubbleState()`, `usePrefs()`, `useTheme()`). The store contains `{ turns, bubbleState, activeError?, prefs: { persistEnabled, theme, version } }` and a closed action surface (`boot`, `setBubble`, `appendTurn`, `setError`, `clearAll`, `togglePersist`, `setTheme`). The orchestrator hook `useConversationLoop()` consumes the store via selectors and is the only caller that issues lifecycle actions (UI components dispatch only `togglePersist`, `clearAll`, `setTheme`).
- **Rationale** *(amended 2026-04-28)*: The previous useReducer + Context choice was correct for the conversation slice in isolation, but the project owner (2026-04-28) requested a global store to (a) avoid React-tree prop drilling for the orchestrator hook and theme toggle, (b) skip the Context provider boilerplate, and (c) carry the same state library across future features. Zustand at ~1 kB is the smallest pay-as-you-go option that satisfies all three. Selectors give granular re-renders (cheaper than Context in non-trivial apps). The action shape from the original reducer translates 1:1 to Zustand setters; the data-model invariants stay intact.
- **Alternatives considered** *(amended 2026-04-28)*: (a) Original useReducer + Context — superseded by owner request; (b) Redux Toolkit — rejected, overkill, ships a much heavier runtime than Zustand for the same surface; (c) Jotai — rejected, atom model fits less naturally to the state-machine shape; (d) Valtio — rejected, proxy mutations are less explicit than Zustand setters and harder to assert against in tests; (e) `useState` everywhere — rejected, the bubble state machine and turn finalization invariants are easier to express in a single store with a closed action set.

## 8. Storage — localStorage with one adapter file

- **Decision**: `src/lib/storage.ts` exposes `loadPrefs() / savePrefs(p) / loadTranscript() / saveTranscript(turns) / clearAll()`. Reads always work. **Writes** go through a guard: `saveTranscript` returns immediately and does nothing if `prefs.persistEnabled !== true`. Prefs writes always go through. `clearAll` removes both keys regardless of prefs.
- **Rationale**: Passes FR-017 (default OFF) and FR-018b/c/d. The adapter is the only file allowed to call `localStorage.*`; an ESLint rule (or a code-review checklist item) enforces this so a future swap to IndexedDB / OPFS is mechanical.
- **Alternatives considered**: (a) IndexedDB — rejected for MVP, payload is small text; complexity not justified; (b) `useLocalStorage` hook — rejected, hides the privacy guard from the call site.

## 9. Mic permission — getUserMedia probe before recognition

- **Decision**: Before the first call to `webkitSpeechRecognition.start()`, the orchestrator calls `navigator.mediaDevices.getUserMedia({ audio: true })`. On success, it immediately stops the resulting tracks (we don't want a hot mic outside `listening`) and proceeds to `listening`. On `NotAllowedError` / `NotFoundError`, the orchestrator dispatches an error action; the bubble does not enter `listening`; `MicPermissionError.tsx` renders. The "Try again" button calls the same probe.
- **Rationale**: webkitSpeechRecognition's permission prompt is implicit and racey on iOS Safari; a `getUserMedia` probe gives us a clean Promise-shaped permission outcome and decouples permission from recognition lifecycle.
- **Alternatives considered**: (a) Let `webkitSpeechRecognition.onerror` surface permission failures — rejected, the error event is non-uniform across browsers and arrives late; (b) `Permissions.query({ name: 'microphone' })` — partially supported; used as a hint where available, but the `getUserMedia` probe remains the source of truth.

## 10. Whisper-via-proxy — documented contingency, NOT adopted

- **Decision**: Do **not** ship Whisper-via-proxy STT in feature 001. Document the trigger and the migration steps so a future feature can pick it up: trigger = SC-001 p95 measured ≥ 3600 ms across a representative sample; migration = swap `src/lib/stt.ts` implementation behind the same exported surface (`startRecognition() / stopRecognition()`), add a `MediaRecorder`-based audio capture, send chunks to the proxy's `/v1/audio/transcriptions` endpoint, return the final transcript on stop.
- **Rationale**: §VI ("Free-Tier First") forbids paid-or-network STT until the free-tier alternative has measured failure. The module boundary in `stt.ts` is precisely the seam this contingency targets, so designing for it now requires zero up-front cost.
- **Alternatives considered**: (a) Ship both and feature-flag — rejected as premature complexity; (b) Hide the contingency from the plan — rejected, a documented escalation path is what §VI demands.

## 11. Tab visibility & cleanup

- **Decision**: The orchestrator subscribes to `document.visibilitychange`. On `hidden`, it calls `stt.stopRecognition()`, `tts.cancel()`, `vad.stop()`, releases any held `MediaStream`, and transitions the bubble to `listening` (idle) so when the user returns the loop is in a clean state. No background-audio support (out of scope per spec).
- **Rationale**: The Web Speech API stops on tab background regardless; making the cleanup explicit avoids the "stuck in `thinking`" failure mode and aligns with FR-021's "no mic hot indefinitely" intent extended to the visibility case.
- **Alternatives considered**: (a) Try to keep the loop alive in the background — rejected, out-of-scope per spec and likely impossible on iOS Safari anyway; (b) Force a full page reload — rejected, destroys in-memory state needlessly.

## 12. Conversation history window

- **Decision**: The system message + the most recent **10 finalized turns** are sent on every chat completion request. Older turns remain in the local transcript display (and in localStorage when persistence is ON) but are not forwarded to the LLM.
- **Rationale**: Spec assumption ("the most recent ~10 turns"). Strictly bounded payload protects §IV (smaller prompts → faster first token). Truncating older turns is acceptable because the conversational tone forgives forgetting; it is *not* acceptable to forget mid-turn references.
- **Alternatives considered**: (a) Send everything — rejected, latency and cost; (b) Sliding token-budget window with summarization — rejected, premature complexity for MVP (§VII).

## 13. Silence policy implementation (FR-021 / SC-010)

- **Decision**: In the orchestrator, when entering `listening`, start two timers: a 30 s "gentle prompt" timer and a 60 s "end turn" timer. Any `onSpeechStart` from VAD cancels both timers; **once cancelled within a turn, neither timer is re-armed for that turn** — VAD `onSpeechEnd` ends the turn directly, or the §15 max-turn cap fires, whichever comes first. The 30 s timer, on fire, dispatches an "AI silence prompt" action that sends a special system message (`"The learner has been silent for ~30 seconds. Send a short, warm encouragement to keep going. ≤ 12 words."`) through the same `ai.ts` → `tts.ts` pipeline; this is **not** counted as a learner turn. The 60 s timer, on fire, transitions `listening → thinking` **without appending any learner turn** (FR-016 — a silent learner has nothing to finalize, and data-model.md's validation rules forbid an empty-text non-error turn), runs the silence-end utterance as a tutor utterance via the same `ai.ts` → `tts.ts` pipeline (still not appended back to `messages` per `contracts/ai-proxy.md`), then transitions to `listening`. `state.turns` is unchanged across the entire silent-end round.
- **Decoupling from STT lifecycle**: The silence timers depend **solely** on VAD `onSpeechStart` / `onSpeechEnd`. STT lifecycle events — including iOS Safari's spontaneous `onend` after ~30 s and the §3 auto-restart logic — do **not** affect these timers. This decoupling is essential because STT can briefly stop and restart mid-utterance while VAD continues to report speech; treating an STT restart as a "silence" event would mis-fire the prompt.
- **Rationale**: Aligns with the resolved spec (~30 / ~60 s). Reusing the AI for the prompt keeps the persona consistent (no hardcoded "still there?" string). Cancelling on first speech is what "after sustained silence" means. Not re-arming on intra-turn pauses prevents ambient hangs of VAD's hangover window from re-triggering the prompt mid-utterance.
- **Alternatives considered**: (a) Hardcoded prompt strings — rejected, breaks FR-025 / persona consistency; (b) Single 60 s cap with no mid-prompt — rejected, breaks SC-010; (c) Reset timer on any audio rather than on VAD speech — rejected, ambient noise would never trigger the prompt; (d) Re-arm timers on every VAD `onSpeechEnd` within the same turn — rejected, conflates "user paused mid-thought" with "user fell silent" and makes the prompt fire mid-utterance.

## 14. Error recovery (FR-019, FR-020)

- **Decision**: `ai.ts` retries `sendChatStream` exactly **once** on a network error or HTTP 5xx, with a 250 ms delay. After the second failure, it throws a typed `AiTransportError`. The orchestrator catches this, dispatches an error action, leaves the learner's transcribed turn in the transcript with no tutor reply attached (per FR-020), shows a brief toast/inline error indicator, and resumes `listening` after at most 10 s total time spent in `thinking` (SC-008). HTTP 4xx (incl. content filter) is not retried; same treatment as 5xx-after-retry.
- **Rationale**: Bounded retry per FR-019. Single retry is enough to absorb transient blips without compounding the §IV budget. The hard 10 s cap implements SC-008 directly.
- **Alternatives considered**: (a) Exponential backoff with N retries — rejected, breaks SC-008; (b) No retry — rejected, transient errors would surface unnecessarily; (c) Auto-resend the user's turn after recovery — rejected, double-charges the user perceptually.

## 15. Maximum continuous-speech turn cap (FR-009)

- **Decision**: Pin the maximum learner-turn duration at **90 seconds** of continuous capture in `listening`. The orchestrator starts a single `max-turn` timer when entering `listening`. Unlike the §13 silence timers, this timer is **not** cancelled by VAD `onSpeechStart`; it counts wall-clock time from `listening` entry. On fire, the orchestrator forces a turn end (transitions to `thinking`) using whatever STT transcript has been captured up to that point — partial finalization is acceptable, the AI replies on what it received, the loop continues. The timer is cleared on any normal turn-end path (VAD `onSpeechEnd`, bubble tap, or §13's 60 s silence end-turn).
- **Rationale**: FR-009 ("a hard cap on turn duration MUST exist; the value is left to the plan, but must be enforced") and the spec's "Very long learner utterance" edge case both require a ceiling that VAD-silence cannot guarantee — a learner reading aloud or in a non-stop monologue may keep VAD continuously hot for minutes. 90 s gives generous room for storytelling (typical practice utterance is 5–30 s) while preventing the loop from breaking down. Wall-clock measurement (not VAD-event-driven) is what makes this cap actually a *hard* cap.
- **Alternatives considered**: (a) 60 s — too short, conflicts with the spec's "speak continuously for minutes" framing as something the system *handles*; (b) 120 s — generous but pushes the §IV budget if STT chunks are large; 90 s strikes the balance; (c) Cancel-on-VAD like the silence timers — rejected, defeats the purpose (a long monologue would never time out); (d) Tie the cap to STT auto-restart count from §3 — rejected, conflates two unrelated mechanisms and makes the cap a side effect rather than an intended policy.
- **Verification**: Component test with fake timers + a sustained-VAD-speech stub (`onSpeechStart` fires, `onSpeechEnd` never fires for ≥ 90 s) asserting the bubble exits `listening` to `thinking` at 90 ± 5 s and that the partial transcript captured by STT up to that point is forwarded to `ai.ts`. Tracked in plan.md's verification matrix as the FR-009 row.

## 16. Styling — UnoCSS with Tailwind-compat preset *(amended 2026-04-28)*

- **Decision**: Adopt `unocss` with the `@unocss/preset-wind3` preset (Tailwind v3-compatible utilities) plus custom shortcuts in `uno.config.ts` for design tokens. Required shortcuts include at minimum: `text-default` → `text-gray-900 dark:text-gray-100`, `text-muted` → `text-gray-500 dark:text-gray-400`, `bg-default` → `bg-white dark:bg-gray-950`, `bg-elevated` → `bg-gray-50 dark:bg-gray-900`, `border-default` → `border-gray-200 dark:border-gray-800`. Vite plugin (`UnoCSS()`) added to `vite.config.ts`. `main.tsx` imports `@unocss/reset/tailwind.css` and the virtual stylesheet `'virtual:uno.css'`. Component code uses utility classes; CSS keyframes for bubble state transitions remain in `index.css` because UnoCSS does not replace `@keyframes` definitions.
- **Rationale**: Owner-requested utility-first styling. Preset-wind3 means class names match the Tailwind-v3 ecosystem (docs, snippets, copy-pasteable examples transfer 1:1). UnoCSS produces a smaller CSS payload than Tailwind, runs at build time with no runtime cost (compatible with §IV latency budget), and HMR is near-instant. Custom shortcuts collapse the dark/light dual-class pattern (`text-gray-900 dark:text-gray-100`) into single semantic names — the project owner's explicit ergonomic preference.
- **Alternatives considered**: (a) Tailwind v4 directly — rejected, heavier setup, slower HMR than UnoCSS for the same class surface; (b) CSS Modules with a dark-class scope — rejected, verbose and noisy for a theme-aware design system; (c) CSS-in-JS (emotion, styled-components) — rejected, runtime cost conflicts with §IV; (d) Plain CSS-only (the original plan) — superseded by owner request.

## 17. Theme system — three modes, dark class on `<html>` *(amended 2026-04-28)*

- **Decision**: Three theme modes — `'light' | 'dark' | 'system'`. Default is `'system'`, which resolves at runtime via `window.matchMedia('(prefers-color-scheme: dark)')` and updates if the OS preference flips. The active resolution is applied by toggling the `dark` class on `<html>` (UnoCSS / Tailwind dark variant). The user's chosen mode is persisted inside the existing `boom:prefs` blob as `prefs.theme`; no new storage key. A small `src/lib/theme.ts` exposes `applyTheme(mode)` (apply class), `resolveTheme(mode): 'light' | 'dark'` (with system resolution), and `subscribeSystemTheme(cb)` (listens on the media query). The Zustand store calls `applyTheme()` whenever `prefs.theme` changes (subscribe). `<ThemeToggle />` inside the SettingsDrawer cycles the user's choice across the three modes; cycling order: `light → dark → system → light`.
- **Rationale**: `dark` class on `<html>` is the canonical UnoCSS/Tailwind dark-variant trigger; using `<html>` rather than `<body>` ensures even the initial HTML chrome respects the mode before React mounts (we set the class as early as possible from `main.tsx`). Three modes cover the three practical user intents (force light, force dark, follow OS) without inventing a fourth. Persisting in the existing `boom:prefs` blob avoids fragmenting localStorage and keeps the storage-adapter contract narrow.
- **Alternatives considered**: (a) Two modes only (light/dark) — rejected, modern apps default to system tracking and users have come to expect it; (b) Data attribute (`<html data-theme="dark">`) instead of class — rejected, UnoCSS dark variant uses `class="dark"` by default and matching that convention is cheaper than reconfiguring; (c) Separate `boom:theme` localStorage key — rejected, fragmenting prefs across keys complicates the existing storage adapter contract for no benefit; (d) CSS custom property switch — rejected, more bespoke than UnoCSS dark utilities and harder to grep.

None introduces a new external network dependency beyond the AI proxy. All are revisitable via plan revision if measurement shows a problem.
